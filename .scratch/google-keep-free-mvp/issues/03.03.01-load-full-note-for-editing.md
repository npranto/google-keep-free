# 03.03.01: Load the full Note for editing

**Status:** in-progress
**Lane:** Standard (a new Owner-scoped read, and it decides the shape the grid and the dialog share)
**Parent:** 03.03-note-editor-dialog.md
**Blocked by:** 03.01
**Unblocks:** 03.03.02

## Purpose

Give the client a way to get one of the Owner's Notes in full - its whole title and body and its
current `version` - because a grid card carries only a 500-character preview and no `version`.

## Scope

- One Owner-scoped read of a single Note by id, returning the full `title`, the full `body` and
  the `version`. It goes through the same Owner scoping as the list views (ADR 0002), takes no
  Owner id from the caller, and answers a missing id and another Owner's id the same way.
- **Open for scope-check:** how the full Note reaches the client. Two options were named when
  03.03 was sized:
  - fetch it when the dialog opens (a Server Action or a route that returns the Note), or
  - pass the full body and `version` to the client with the grid (this changes `NoteCardData`,
    which exists to keep the full body out of the grid on purpose).
  Whichever is picked, the dialog needs `version` too, which `NoteCardData` does not carry.
- Whether a Trashed Note can be read through it. The read-only variant for a Trashed Note is out
  of scope (07), so the default is Active only; scope-check confirms.
- Integration tests through the real database (there is no screen yet).

## Out of scope

The dialog, any change to `NoteCard`, the `Dialog` primitive, `useAutosave` wiring, the grid
revalidation behavior after a save.

## Acceptance criteria

- [ ] The read returns the full title and body, including a body longer than the 500-character
      card preview, unchanged, plus the Note's current `version`.
- [ ] Another Owner's Note, a missing id and a malformed id all get the same answer, and reveal
      nothing about which one it was.
- [ ] Signed out, the read redirects like every other Owner-scoped call.
- [ ] The grid still receives no full body unless scope-check chose to pass it, and the choice
      is recorded under `## Decisions`.

## Relevant spec sections

"Edit / autosave a Note" journey; the Note model (`version`); ADR 0002 (Owner scoping).

## Architecture/design constraints

Reuse the existing Owner-scoping path in `lib/notes/queries.ts`; do not add a second way to
filter by Owner. `toNoteCard` and `NoteCardData` stay the only door into the grid unless the
scope-check design says otherwise, and then the change to them is explicit.

## Testing expectations

Integration (real database, as `lib/notes/notes.integration.test.ts` already does): full body
over the preview limit, another Owner's id, a missing id, a malformed id. Unit tests only if a
mapper is added. No E2E: nothing on a screen calls this yet. 03.03.02 proves it end to end.

## Demo instructions

Run the integration suite and read the new cases: a 20,000-character body comes back whole with
its `version`, and another Owner's id comes back as not found.

## Likely files/areas

`lib/notes/queries.ts` or `lib/notes/actions.ts`, `lib/notes/card.ts` (only if the grid shape
changes), `lib/notes/notes.integration.test.ts`.

## Risks / conflict hotspots

The full-body choice touches the shape the grid is built on (`NoteCardData`, `NoteGrid`). A
fetch-on-open read must not leak another Owner's Note through a guessable id.

## Decisions

- 2026-10-31 (scope-check, design): the full Note reaches the dialog through a **Route Handler**,
  `GET /api/notes/[id]`, fetched when the dialog opens. It returns `{ id, title, body, version }`
  as JSON, a 404 with one body for another Owner's id, a missing id and a malformed id, and
  `Cache-Control: private, no-store`. The Owner filter reuses `selectOwnedNotes`; the id is checked
  as a uuid before the query. Rejected: a Server Action `getNote` (the Next 16 docs in this repo
  say actions are for mutations and are dispatched one at a time, so a read queues behind a save in
  flight: `node_modules/next/dist/docs/01-app/02-guides/backend-for-frontend.md:902`), and the full
  body in the grid props (breaks `card.ts`'s no-full-body guarantee, bloats the page payload, and can
  open a reopened Note with a stale `version`). Principle: Design it twice. It is the repo's first
  `app/api` route, which ADR 0001 allows ("a few route handlers"). 04's "Reload" reuses it.
- 2026-10-31 (scope-check, states): the read returns any Note the Owner owns, in any state, not
  Active only. 06 (Archived) and 07 (Trashed, read-only) then need no change to it; nothing new is
  exposed, and `updateNote` already rejects a save to a Trashed Note.
- 2026-10-31 (scope-check, risks and abuse cases to test): other Owner's id, missing id and
  malformed id answer identically (status and body); a signed-out call redirects; the response
  carries `private, no-store`. Carried to 03.03.02: signed out mid-session, `fetch` follows the
  redirect and gets HTML, so a non-JSON answer must show as an error in the dialog (guess, not run).
- 2026-11-01 (review, D1): the review found that the route contradicts `docs/architecture/system.md`
  ("No `/api/*` route handlers", reads in Server Components, client reads as Server Actions as in
  `searchNotes`). Scope-check had read ADR 0001 (which allows "a few route handlers") but not
  `system.md`, and had overstated the queue argument (the real cost is one save round trip, and
  search already accepts it). Options put to the owner: A (Server Action, recommended by the
  reviewer), C (keep the route and amend the docs), B (full body in grid props). **The owner chose
  C.** `system.md` now lists `GET /api/notes/[id]` as the one `/api` route besides the future Cron
  endpoint, with the reasons, and `flows.md` has an "Open a note in the editor" journey. Accepted
  trade-off: the app has two ways to read from the client (this route, and Server Actions such as
  `searchNotes`), so later reads should say why they use the one they use. No ADR was written.
