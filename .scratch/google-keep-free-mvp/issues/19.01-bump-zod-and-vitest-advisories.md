# 19.01: Bump zod, vite and vitest to clear their audit advisories

**Status:** open
**Classification:** DEPENDENCY (found in 03.01's `/ns-to-quality-check`, stage 8; not part of the spec's acceptance criteria)
**Lane:** Standard (the lockfile moves the schema library the server validates input with, and the test runner behind both suites)
**Parent:** ✅19-bump-next-security-advisories.md
**Blocked by:** None (can start immediately; do it before 16, the final release checks, so those start from a clean audit)
**Unblocks:** None

## Purpose

`npm audit --omit=dev` reports a high-severity `zod` advisory, and `npm audit` reports a second
high one in `vite` (through `vitest`). Move both to patched releases so the audit is clean of
everything that has a non-breaking fix.

## Context

On 2026-10-30 `npm audit` reported 8 findings (2 high, 6 moderate), none caused by a diff and
none introduced by ticket 03.01, which touched no dependency file.

| Package | Severity | Reaches production | Advisory | Fixed in |
|---|---|:---:|---|---|
| `zod` 4.6.5 (direct) | high, CVSS 7.5 | yes | GHSA-mrhx-c7xc-m3w5: validation can exhaust memory on oversized constrained collections | 4.6.6 (4.6.7 is current) |
| `vite` 8.3.2, through `vitest` | high | no, dev and test only | `launch-editor` and dev-server advisories (arbitrary command execution for some editors, files served outside `server.fs.allow`) | a non-breaking update (`fixAvailable: true`) |
| `vitest` 4.1.11 and `@vitest/mocker` | moderate | no | code injection through manual mock registration | a non-breaking update |

The `zod` advisory is not reachable from this app today: `lib/env.ts` and
`lib/notes/validation.ts` are the only importers and neither builds an array, set, map, record or
tuple schema. It is still a direct dependency with a high advisory, and a future schema could
change that. `package.json` already says `^4.6.5`, so 4.6.7 is allowed; only the lockfile pins
4.6.5. `eslint-plugin-react-hooks` and `zod-validation-error` resolve to the same copy.

## Scope

- Raise the `zod` floor in `package.json` to `^4.6.6` and update the lockfile to the current 4.6.x,
  so the vulnerable version cannot be installed again.
- Update `vitest` (and with it `vite` and `@vitest/mocker`) to the patched, non-breaking release
  `npm audit` names. Read the release notes for anything between 4.1.11 and the target that
  touches the two config files before changing them.
- Re-run types, lint, format, the unit and integration suites, build and E2E.

## Out of scope

- The moderate `drizzle-kit`, `esbuild` and `@esbuild-kit/*` chain. npm's suggested fix is
  `drizzle-kit@0.18.1`, which is a downgrade, and ticket 19's close judged an `npm` override not
  worth the change for a dev-only tool. It stays an accepted risk unless that changes.
- Any other package upgrade, including `next`, and using anything new in `zod` or `vitest`.
- Adding a scheduled dependency audit to CI, and running the integration suite in CI (ticket 16).

## Acceptance criteria

1. `npm audit --omit=dev` reports 0 vulnerabilities.
2. `npm audit` no longer lists `zod`, `vite`, `vitest` or `@vitest/mocker`. What remains is only the
   `drizzle-kit` chain named above.
3. `package.json` no longer admits `zod` below 4.6.6, and `package-lock.json` resolves one copy of
   `zod` at 4.6.6 or later, including the copies used by `eslint-plugin-react-hooks` and
   `zod-validation-error`.
4. Types, lint, format, the unit suite (86 tests today), the integration suite (30 today), the
   build and the E2E suite (26 today, none skipped) all pass locally with the same counts, and on
   the PR including `E2E (preview)`.
5. The diff changes only `package.json`, `package-lock.json` and ticket or doc files. Source files
   are left alone unless a release note makes a change unavoidable, and then it is recorded under
   Decisions.

Nothing here is visible on a preview link, so there is no click-through. A non-engineer can read
the before and after `npm audit` output on the PR.

## Testing seam

The existing suites are the proof: the unit tests assert the validation messages and limits, the
integration tests run the real schemas against the database, and `npm run build` runs
`lib/env.ts` through the `prebuild` connection check. `npm audit --omit=dev` and `npm audit`,
before and after, are the evidence for criteria 1 and 2. No new test is needed.

## Dependencies

`zod` (direct), `vitest` (direct, dev), `vite` and `@vitest/mocker` (through `vitest`).

## Demo

Run `npm audit --omit=dev` and `npm audit` before and after, and show the zero and the shorter
list. Then run `npm test`, `npm run test:integration` and `npm run e2e` with the same counts.

## Risks

- Low to medium. A `zod` patch could change an error message that a test or the UI shows; the
  unit tests assert messages, and `updateNote` returns the first issue's text to the client.
- A `vitest` update could change how the two `.mts` configs load; the integration config sets its
  own timeouts for a suspended Neon compute and must keep them.
- Keep it a single-purpose PR, as ticket 19 did.

## Undo

Revert the PR. There is no data step, no migration and no env change, and the version tag moves
forward as usual.

## Relevant architecture constraints

`lib/env.ts` validates the environment at startup with `zod` and the build's `prebuild` check
loads it, so a broken `zod` update fails the build early. The two vitest configs are
`vitest.config.mts` and `vitest.integration.config.mts`.

## Decisions

### What 19.01 covers (2026-10-30, user)
- **Pick:** `zod` (the only advisory in what ships), plus `vite` and `vitest` (dev only, a non-breaking update).
- **Rejected:** `zod` only, leaving a high dev-only advisory open that has a cheap fix; and everything `npm audit` reports, which pulls in the `drizzle-kit` chain whose suggested fix is a downgrade.
- **Principle:** one purpose per PR, and fix what has a non-breaking fix.
- **Undo:** trivial, a revert.
