# 02.03.06: /forge-test rendering demo page (server, client, streamed, lazy)

**Status:** closed
**Lane:** Standard (proposed: an external API, several rendering modes on one page, and a new public route)
**Parent:** ✅02.03-composer-and-notes-grid.md
**Blocked by:** None (needs no credentials, integrations or database)
**Unblocks:** None

## Purpose

Put a public demo page at `/forge-test` that shows, side by side, every way a Next.js App Router page can render. Most of the page is server rendered from data fetched in the server component. The rest are small sections that each use a different mode, so the page doubles as a working reference for what runs where. Dummy UI and dummy data only.

## Scope

A new public route `/forge-test` (`app/forge-test/page.tsx`, plus small co-located components) outside the `(app)` route group, so it needs no sign-in, the same as `/try-out`. Tailwind and the existing `ui` components only. The page exports its own `metadata`: a title, and `noindex` for as long as it is a demo.

Dummy data comes from one public, keyless API (JSONPlaceholder or DummyJSON; pick one at scope-check and record why). No env var, no new dependency.

Each section carries a visible label naming its rendering mode:

1. **Server rendered (the majority of the page).** Several sections whose data is fetched in the server component at request time and arrives in the first HTML: for example a list of posts, a users grid and a todo summary.
2. **Server rendered, cached.** A server fetch with a revalidate window (`fetch(url, { next: { revalidate } })`), labelled with the window.
3. **Client component, no fetching.** A `"use client"` section with local state only, such as a counter or a tab switcher.
4. **Client-side fetch.** A `"use client"` section that fetches after mount, with visible loading and error states.
5. **Streamed.** A server section behind `<Suspense>` with a skeleton, whose fetch is slow enough to stream in after the shell (a delayed endpoint, or a short awaited delay).
6. **Lazy loaded.** A client section loaded on demand with `next/dynamic` (or `React.lazy`), shown after a click or when scrolled into view, with a placeholder until it loads.

## Out of scope

Real content or copy, a database, auth or Clerk changes, any `/api/*` handler of our own, new dependencies, linking the page from the header, sidebar, `/try-out` or anywhere else, search indexing (no sitemap, no `robots.txt` change), analytics, and changes to existing pages, layouts or shared components.

## Acceptance criteria

- [x] `/forge-test` answers 200 for a signed-out visitor and shows every section above, each labelled with its rendering mode.
- [x] The server rendered sections (1 and 2) have their fetched data in the served HTML with JavaScript off: a plain request for the page contains the dummy data, and the server sections make up most of the page.
- [x] Sections 4 and 6 do not have their fetched or lazy content in the served HTML. Their data and lazy component appear after hydration, and section 4 shows loading, then data (and an error state when its request fails).
- [x] Section 5 streams: the shell and its skeleton arrive first, then the content replaces the skeleton without a full reload.
- [x] If the dummy API is down or slow, the page still answers 200: a failing section shows an inline message and the rest renders. No `500`, no blank page.
- [x] Layout holds at 390, 820 and 1440 wide with no horizontal scroll, and text stays readable.
- [x] The page sends `noindex`, and no other route, layout, component or dependency changes (`package.json` is untouched apart from the release bump).

## Testing expectations

- A signed-out E2E spec `e2e/forge-test.spec.ts`, tagged `@smoke` like `e2e/try-out.spec.ts`, since the page needs no sign-in: sections and labels are present, `noindex` is set, and no horizontal scroll at the three widths.
- A no-JavaScript check that the server sections' data is in the served HTML (a plain `request` GET, or a context with JavaScript disabled), and that sections 4 and 6 are not.
- A test of the failure path with the dummy API blocked (`page.route` on the API origin from the browser, and a way to force the server fetch to fail), so the 200 and inline-message criterion has a kept test.
- The tests must not depend on the dummy API being up or returning particular rows: assert structure and the presence of data, and use a failure double where the API must be down.

## Decisions

Settled at scope-check (2026-10-26, proposed by agent, evidence from the Next 16.4.2 docs shipped in `node_modules` and a probe of the API):

- **Dummy API: DummyJSON.** Keyless, CORS open to any origin, `select` and `limit` shrink the payloads, and `?delay=<ms>` slows any endpoint (1.5 s asked, 1.75 s measured), which the streamed section needs. JSONPlaceholder has no delay option.
- **Cache Components stays off.** The default `fetch` is "auto no cache": fetched once at build time when the route is prerendered. So the request-time sections use `cache: "no-store"`, which also makes the route dynamic (`ƒ` in the build output; `cache-control: private, no-store`). The cached section uses `next: { revalidate: 60 }`, which needs no Cache Components.
- **Lazy section:** `next/dynamic` with `ssr: false` is only allowed in a Client Component, so a small client wrapper holds it and mounts it on a button click. Its code is a separate chunk that downloads with the click.
- **Failure:** one fetch helper (`lib/forge-test/dummy-api.ts`) returns `{ ok }` and never throws, with a 5 second timeout. Each section shows an inline "unavailable" message, so the page stays 200. A browser test cannot block a server-side fetch, so the server failure path is covered by unit tests (a mocked `fetch`), and the browser failure path by an E2E test that aborts the client request.
- **Tests do not depend on the API:** the E2E accepts `ready` or `unavailable` for the server cards, and answers the client fetch itself with `page.route`. One test (streaming) needs the real slow API and skips itself, with a stated reason, when the API is unreachable.
- **Linking:** nothing links to the page.
