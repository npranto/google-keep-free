# 02.04: Switch the package to ES modules (`"type": "module"`)

**Status:** open
**Lane:** Standard (one line in `package.json`, but it changes how Node reads every `.js` and `.ts` file, so the tools that load files through Node must each be proven)
**Parent:** ✅02-create-and-persist-a-note.md
**Blocked by:** None
**Unblocks:** None

## Purpose

`package.json` has no `"type"` field, so Node reads every `.js` and `.ts` file in the package as CommonJS and has to guess when a file uses ESM syntax. The whole codebase is already written as ESM (`tsconfig.json` is `module: esnext` with `moduleResolution: bundler`, and ESLint, PostCSS and both Vitest configs are ESM files).

The guessing costs a visible warning on every build: `MODULE_TYPELESS_PACKAGE_JSON` for `lib/db/index.ts`, printed by the `prebuild` connection check (`lib/db/check-connection.mts` imports it). It was found in the 02.03.04 quality check. Setting `"type": "module"` fixes the cause once, instead of renaming one file at a time as 02.02.02.01 did for the Vitest configs.

## Scope

- Add `"type": "module"` to `package.json`.
- Fix every file that stops working because of it. Candidates, to confirm by running each tool rather than by reading (none of this is proven yet):
  - `playwright.config.ts` and `e2e/*.ts`: they switch from CommonJS to native ESM loading. Check the extensionless relative imports (`./e2e/env`, `./fixtures`, `./sign-in`), and any `require`, `__dirname` or `import.meta` use. A search found none today.
  - `drizzle.config.ts`: loaded by `drizzle-kit`. It already imports `./lib/env.ts` with the extension.
  - `next.config.ts` and `proxy.ts`: Next supports both module types, so this is the lowest risk.
  - `lib/db/check-connection.mts` and the files it imports: the `prebuild` path.
  - Docs or comments that describe the CommonJS behavior, if any are found when searching.

## Out of scope

Any change to `tsconfig.json`, any new dependency, and renaming files that already work. The Vitest configs stay `.mts`, and the other already-ESM config files stay as they are. Prettier in CI and the Escape key's IME guard in the composer, which were found alongside this in the 02.03.04 quality check, are separate follow-ups.

## Acceptance criteria

- [ ] `package.json` has `"type": "module"`, and `npm run build` prints no `MODULE_TYPELESS_PACKAGE_JSON` warning (measured before and after).
- [ ] Typecheck, lint, format check and `npm test` pass with the same number of tests, and `npm run test:integration` passes with the same number of tests against the real database.
- [ ] `npm run e2e` passes with the same number of tests as before, none skipped, against a fresh local build.
- [ ] `npm run db:generate` reports no schema changes and creates no file (it proves `drizzle-kit` still loads its config).
- [ ] `npm run dev` starts, and a signed-out visit to `/` redirects to `/sign-in`.
- [ ] CI is green on the PR: Healthcheck, `E2E (preview)` and the preview deployment build.
- [ ] Every changed file besides `package.json` is listed in the PR with the tool that forced the change.

## Testing expectations

No new tests. The proof is the existing suites plus the missing warning, measured before and after, and the `db:generate` and `dev` checks above. Nothing is user-visible, so there are no new E2E tests or screenshots.

## Risks

- Playwright could fail to resolve the extensionless imports in the specs under native ESM. Guess: it handles TypeScript specs itself, but this is unproven. The full E2E run decides.
- `drizzle-kit` could fail to load `drizzle.config.ts`. Guess: it works, because the config already imports with an extension. `db:generate` decides.
- A tool in CI that the local run does not use, such as the Release or Rollback workflows, could read a package file. The PR's CI run decides, and those workflows only call `npm run` scripts.

## Undo

Revert the PR. Config only, no data, nothing shipped to users.

## Decisions

### `"type": "module"`, reversing the choice in 02.02.02.01 (2026-10-22, requested by the user)

- **Pick:** switch to `"type": "module"`. 02.02.02.01 chose `.mts` instead and rejected this as "too wide for a warning". The wider reason has changed: the build now prints a second warning from the same cause, and the codebase is ESM throughout, so the per-file renames are a patch for something one line fixes.
- **Rejected:** keeping `.mts` renames. Each new script Node loads would need the same treatment.
- **Evidence:** the search for `require`, `__dirname` and `module.exports` found none in `app`, `components`, `lib`, `e2e` or the root configs *(measured)*. That each tool loads cleanly under ESM is *unproven* until the acceptance runs above.
- **Undo:** trivial, one line plus whatever files were forced to change.
