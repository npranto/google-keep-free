## Purpose

Let the server create a Note for the signed-in Owner, with the ownership and length
rules proven on the real database before any UI exists.

## Scope

- `lib/notes/actions.ts`: `createNote`, its own Server Action. Parses input first with the
  02.02.01 schema, inserts with `ownerId: await getOwnerId()` in the same statement,
  returns the new `id` and `version`, then `revalidatePath("/")`. On a parse failure it
  returns the `validation` error and touches neither the database nor `getOwnerId`.
- `lib/notes/actions.test.ts`: unit, with the database mocked, proving a rejected input
  makes no database call.
- `npm run test:integration` (vitest, `*.integration.test.ts`, loads `.env.local`, its own
  config), left out of `npm test` because the Healthcheck `test` job has no database.
- `lib/notes/notes.integration.test.ts`: real database, `getOwnerId` mocked as the only
  identity seam, rows tagged with a unique test Owner and removed afterward.

## Out of scope

Any UI, `updateNote`, autosave, queries (02.02.03), rate limiting.

## Acceptance criteria

- [x] `createNote` with content inserts one Note as `active`, owned by the caller, and
      returns its `id` and `version`.
- [x] `createNote` with empty title and empty body (including whitespace only) inserts no
      row and returns a `validation` error.
- [x] A title over 300 or a body over 20000 characters is rejected before any database
      call, and exactly 300 and 20000 are accepted.
- [x] A client-supplied `ownerId` in the input is ignored.
- [x] `npm run test:integration` runs against the real database, and `npm test` does not.

## Testing expectations

Unit: a rejected input makes no database call and does not read the Owner.
Integration (real database): the row is `active` and owned by the mocked Owner, an empty
draft never persists, over-limit is rejected, the exact limits are accepted, an
`ownerId` in the input is ignored. Nothing is user-visible yet, so no E2E.

## Decisions

### Keep as one ticket (2026-10-14, user)
- **Pick:** no further split. The ticket already passes the sizing test, and the harness has nothing to run until `createNote` exists.
- **Rejected:** splitting the harness from the action, which would ship a harness with no test using it.

### How is the integration suite configured? (2026-10-14, user)
- **Pick:** a separate `vitest.integration.config.ts`, with `*.integration.test.ts` excluded from `vitest.config.ts`. The database comes from the environment: the config loads `.env.local` only when it exists and never overrides a variable that is already set, so local, CI and a Neon branch differ by `DATABASE_URL` alone.
- **Rejected:** one config with vitest projects, because a bare `vitest` or an editor runner would also run the integration project against the shared database. Also rejected: reading `.env.local` unconditionally, because CI wiring would need a config change later.
- **Evidence:** the 3-line alias repeat is the accepted cost. Principle: Guard at the boundary.
- **Undo:** two-way door, config files only.

### Correct flows.md in this PR (2026-10-14, user)
- **Pick:** change `flows.md:48` from `ActionResult<Note>` to the `{ id, version }` this ticket returns, so the docs match the code.
- **Rejected:** leaving it for 02.03, because the doc would stay wrong and might be forgotten.

### Spam creation is not stopped here (2026-10-14, accepted by the ticket)
- Rate limiting is out of scope per this ticket. Clerk auth bounds who can call `createNote`. Accepted.
