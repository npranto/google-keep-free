# 02.01: Notes table and migration

**Status:** closed
**Lane:** Standard (additive schema change: a new table and two enums, no existing data)
**Parent:** ✅02-create-and-persist-a-note.md
**Blocked by:** 01 (Application foundation)
**Unblocks:** 02.02

## Purpose

Give the app somewhere to keep Notes. Nothing reads the table yet, so this is safe to
land on its own.

## Scope

Define the full `notes` table in `lib/db/schema.ts` per `docs/architecture/data-model.md`:
all columns (`id`, `owner_id`, `title`, `body`, `state`, `color`, `pinned`, `version`,
`created_at`, `updated_at`, `trashed_at`), the `note_state` and `note_color` enums, and
both indexes `(owner_id, state)` and `(owner_id, updated_at)`. Generate the migration with
`npm run db:generate`, commit it, and apply it to the local database with
`npm run db:migrate`. All columns now, even though only `active` is used, so later
tickets need no migration for them.

The `note_color` enum takes the 11 tokens fixed in `docs/design/ui-spec.md` section 19:
`default`, `coral`, `peach`, `sand`, `sage`, `fog`, `storm`, `dusk`, `blossom`, `clay`,
`chalk`. `data-model.md` still says the list is "settled during the design-contract
phase", so update that line to name them.

## Out of scope

`labels` and `note_labels` (tickets 10 and 12), any query or action, any UI.

## Decisions

### Which databases get the migration? (2026-10-13, user)
- **Pick:** local and Preview share one database, Production is separate. The agent migrates the `.env.local` database, which covers Preview. The user applies the same migration to Production at the release stop.
- **Rejected:** automating it in `release.yml`, because migrations are applied by hand by design (`drizzle.config.ts`) and it would need a Production secret in CI.
- **Evidence:** stated by the user (measured). Vercel keeps the values encrypted, so the agent could not check.
- **Undo:** two-way door while the table is empty: `DROP TABLE notes; DROP TYPE note_state, note_color` on each database.

### Which tokens go into `note_color`? (2026-10-13, user)
- **Pick:** A. All 11 from `ui-spec.md` section 19.
- **Rejected:** B, only `default` now and the rest added in ticket 09 (an extra migration, and the picker ticket would own the palette). C, a `text` column with Zod validation (departs from the spec and lets any non-app writer insert bad values).
- **Evidence:** Postgres can add and rename enum values but not remove them (inferred). Tokens are names, so shades can change in CSS without a migration.
- **Principle:** name things for what they are, not how they look today.
- **Undo:** one-way door for removing a token only. Adding and renaming are easy.
- **Decided by:** user.

### Where do the enum value lists live? (2026-10-13, user)
- **Pick:** A. `noteStates` and `noteColors` are exported from `schema.ts` and feed `pgEnum`.
- **Rejected:** B, `lib/notes/constants.ts` now. It is one more file with one caller today. Move them there when a client component needs them (ticket 09 at the latest), because a client importing `schema.ts` would pull Drizzle into the browser bundle.
- **Evidence:** `schema.ts` has no importer besides `drizzle.config.ts` (measured).
- **Principle:** subtract before you add.
- **Undo:** trivial.
- **Decided by:** user.
