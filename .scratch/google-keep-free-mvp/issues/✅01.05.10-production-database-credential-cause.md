## Purpose

Learn why Neon rejected the old Production `DATABASE_URL`, so it does not happen again at the next rotation. See `docs/incidents/0001-production-database-credential-rejected.md`. Only the owner can do this: it needs the Neon and Vercel dashboards.

## Scope

- In the Neon dashboard, check whether the `neondb_owner` password was reset, or the role or branch changed, between 2026-10-09 (when the variable was created) and 2026-10-15.
- Record which of these it was: a reset after the variable was set, a stale or mistyped value from setup, or something else. Do not paste the connection string anywhere.
- Add a short "Rotating the database password" note to `docs/agents/workflow.md` or the README: where the string comes from (pooled connection, "-pooler" host), that Vercel needs the Production variable updated and a redeploy afterwards, and that Preview and local use a different string.

A health check (01.05.08), the Rollback fix (01.05.09), any secret in the repo.

## Decisions

### Close without the investigation (2026-10-26, decided by the owner)

- **Pick:** close the ticket. The owner will not check the Neon and Vercel dashboards, so the cause of the 2026-10-15 rejection stays unknown and no rotation note is written.
- **Not done:** both acceptance criteria stay unchecked on purpose. The postmortem's Root cause section still says the cause is not known.
- **What still covers the risk:** 01.05.08 shipped a `prebuild` check that stops a build whose `DATABASE_URL` Neon rejects (v0.2.26, PR #55), so a bad credential is caught at the next deploy and not by a user. It does not catch a credential that goes bad between deploys.
- **Reopen if:** a credential is rejected again, or before the next password rotation.
