# 03.02: `useAutosave` hook

**Status:** closed
**Lane:** Standard (the concurrency logic in the autosave design, with no screen to catch a mistake)
**Parent:** 03-edit-a-note-with-autosave.md
**Blocked by:** None (the save function is injected, so it does not need 03.01)
**Unblocks:** 03.03

## Purpose

A client hook turns a stream of edits into saves: debounced, flushed on demand, one in flight at
a time, with a status a screen can show.

## Scope

- `components/notes/use-autosave.ts`: takes the current values and a `save` function it is
  given, and returns the status (`idle | saving | saved`) and a `flush()`.
- Debounce: 1 second after the last edit.
- Flush, bypassing the timer: `flush()` for blur and dialog close, and a `visibilitychange`
  listener (best-effort, as the spec says).
- Serialization: only one save in flight; an edit made mid-save is queued and sent right after
  the in-flight save resolves. The queue holds the latest values only.
- Status: `saving` while in flight, `saved` for about 2 seconds, then back to `idle`. The
  `conflict` state is added by 04.
- The hook never calls a Server Action itself. 03.03 passes `updateNote` in.

## Out of scope

The `conflict` state and its banner (04), the `updateNote` action (03.01), the dialog and its
live region (03.03), retry after a failed save.

## Acceptance criteria

- [x] Typing stops for 1s, then exactly one save fires with the latest values.
- [x] A flush saves immediately and cancels the pending timer, so the same edit is not saved
      twice.
- [x] A flush with nothing changed since the last save does not call `save`.
- [x] While a save is in flight, newer edits never start a second save. The latest edit is sent
      once, right after the first resolves.
- [x] The status goes `saving` then `saved` then `idle` after about 2s.
- [x] Hiding the tab triggers a flush.

## Relevant spec sections

Autosave section (Debounce, Flush, Serialization, Status feedback).

## Architecture/design constraints

All debounce, flush and queue logic lives in this hook, not in the Server Action (spec,
Autosave). The hook has one public surface (`flush`, status) and hides the timer, the in-flight
flag and the queue, so 04 can add a conflict state without touching callers.

## Testing expectations

Unit, with fake timers and a fake `save` that the test resolves by hand: every acceptance
criterion above, plus unmount mid-timer. Each test is seen failing for the intended reason
(for example, serialization with the in-flight guard removed). No E2E: no screen yet.

## Demo instructions

Run the unit suite and read the cases: debounce, flush, queued edit, status sequence.

## Likely files/areas

`components/notes/use-autosave.ts` and its test file.

## Risks / conflict hotspots

A save that fails has no defined behavior yet (04 covers conflicts only). The hook must not
swallow the failure silently: decide in scope-check whether it surfaces an `error` status now or
leaves it for 04.

## Decisions

- 2026-10-30 (scope-check): **Test seam: A.** Test the real hook through React with
  `renderHook` and fake timers. Adds dev dependencies `jsdom`, `@testing-library/react` and
  `@testing-library/dom`; the test file opts in with `// @vitest-environment jsdom`, so
  `vitest.config.mts` and the existing tests are untouched. Rejected: A-lite (jsdom plus a
  hand-written `renderHook`: we would maintain a helper testing-library already maintains) and
  B (a framework-free engine under the hook: one caller, state in two places, and the
  visibilitychange, unmount and stale-`save` wiring would stay unit-untested). Principle: test
  behavior, not implementation.
- 2026-10-30 (scope-check): **Failed save: `error` status now.** Status is
  `idle | saving | saved | error`. A `save` that returns `{ ok: false }` or throws counts as a
  failure; the values stay unsaved, so the next edit or flush sends them again. No timer-based
  retry. 03.03 shows the message; 04 adds `conflict`. The spec lists four states, so
  `spec.md` "Status feedback" gets `error` in this ticket (docs change with the code).
  Rejected: leave it for 04 (03.03 ships first, so a failed save would be invisible).
  Principle: observable or not done.
- 2026-10-30 (scope-check, plan line, no objection raised): **Unmount flushes** an unsaved
  edit, so an edit is never dropped silently. Close in 03.03 flushes first, so the unmount
  flush then finds nothing changed and does nothing.
- 2026-10-30 (review I1, nit, kept as is on purpose): **no timeout on a save in flight.** A
  timeout would allow a second save while the first may still land, which breaks the
  one-in-flight rule and makes the version check reject one of them. A stalled request fails
  when the browser gives up, and the queue then drains. The reason is a comment at the
  `inFlight` flag. The user asked to fix all findings; the fix for this one is the comment.
- 2026-10-30 (scope-check, plan line): the hook calls the **latest** `save` at fire time, so
  callers need not memoize it. `save` is typed `(values) => Promise<ActionResult<unknown>>`,
  reusing `lib/shared/result.ts`, so 04 can read `error.kind` without changing the contract.
