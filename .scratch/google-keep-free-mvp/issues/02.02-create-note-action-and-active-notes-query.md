# 02.02: createNote action and active Notes query

**Status:** open
**Lane:** Standard (shared hot files `actions.ts` and `queries.ts`; an ownership boundary)
**Parent:** 02-create-and-persist-a-note.md
**Blocked by:** 02.01
**Unblocks:** 02.03

## Before this ships

- The Production database must have migration `0000_nebulous_ogun` applied by hand. 02.01 shipped the code and the local and Preview database only, so without it `/` returns a 500 in Production.
- From the 02.01 review: check the `getActiveNotes` query plan, and note that `drizzle(sql)` in `lib/db/index.ts` has no `{ schema }`, so `db.query.notes` is unavailable until it is added.

## Purpose

Let the server create a Note for the signed-in Owner and list that Owner's Active Notes,
with the ownership and length rules proven on the real database before any UI exists.

## Scope

- `lib/notes/validation.ts`: Zod schema for create input (title at most 300, body at most
  20000, and not both empty) and the limits as exported constants for the UI to reuse.
- `lib/shared/result.ts`: `ActionResult<T>` with the one error kind this ticket needs,
  `validation`.
- `lib/notes/actions.ts`: `createNote`, its own Server Action. Parses input first, inserts
  with `ownerId: await getOwnerId()` in the same statement, returns the new `id` and
  `version`, then `revalidatePath("/")`.
- `lib/notes/queries.ts`: private `selectOwnedNotes(...where)` that calls `getOwnerId()`
  itself and orders by `pinned DESC, updated_at DESC`, and `getActiveNotes()` on top of it.
- `npm run test:integration` (vitest, `*.integration.test.ts`, loads `.env.local`), left
  out of `npm test` because the Healthcheck `test` job has no database.

## Out of scope

Any UI, `updateNote`, autosave, the other view queries, rate limiting.

## Acceptance criteria

- [ ] `createNote` with content inserts one Note as `active`, owned by the caller, and
      returns its `id` and `version`.
- [ ] `createNote` with empty title and empty body (including whitespace only) inserts no
      row and returns a `validation` error.
- [ ] A title over 300 or a body over 20000 characters is rejected before any database
      call, and exactly 300 and 20000 are accepted.
- [ ] `getActiveNotes()` returns only the caller's Active Notes. A second Owner's session
      never sees them.
- [ ] A client-supplied `ownerId` in the input is ignored.

## Testing expectations

Unit: the Zod schema at 300/301 and 20000/20001, and empty input.
Integration (real database, `getOwnerId` mocked as the only identity seam, rows tagged
with a unique test Owner and removed afterward): owner scoping, empty draft never
persists, over-limit rejected, ignored `ownerId`. Nothing is user-visible yet, so no E2E.

## Decisions

### How does a query get its Owner? (2026-10-13, proposed by agent, pending approval)
- **Pick:** A. `selectOwnedNotes(...where)` calls `getOwnerId()` itself, and `createNote` puts `ownerId: await getOwnerId()` in its insert. No caller passes an Owner.
- **Rejected:** B, callers pass the Owner id. Every future query would have to remember it, and a wrong id compiles.
- **Evidence:** spec "Authorization" and ADR 0002 (inferred).
- **Principle:** make the wrong call impossible.
- **Undo:** trivial, it is code only.
