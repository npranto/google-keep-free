# 03.03.02: Edit a Note in a dialog

**Status:** in-progress
**Lane:** Standard (the first dialog, and the shared file that tickets 04 to 10 fill in)
**Parent:** 03.03-note-editor-dialog.md
**Blocked by:** 03.01, 03.02, 03.03.01
**Unblocks:** 04

## Purpose

An Owner can click a Note, edit its title and body in a dialog with no Save button, see
"Saving…" then "Saved", and find the edit still there after a reload.

## Scope

- `components/notes/NoteEditorDialog.tsx`: a centered `Dialog` with title and body fields and an
  empty toolbar shell. It wires `useAutosave` (03.02) to `updateNote` (03.01), flushes on blur
  and on close, and keeps the Note's current `version` from each save's result.
- The shadcn `Dialog` primitive in `components/ui` (not installed yet).
- `components/notes/NoteCard.tsx`: clicking a card opens the dialog.
- A `role`-correct `aria-live="polite"` status region showing "Saving…" and "Saved" (fades after
  about 2s).
- Using the full-Note read from 03.03.01 (shipped, v0.2.50): when the dialog opens it fetches
  `GET /api/notes/<id>` and fills its fields from `{ id, title, body, version }`, so it opens with
  the whole body and the current `version` (a card carries only a 500-character `preview`). The
  route answers `404 {"error":"not_found"}` for a missing or other Owner's Note, sends
  `Cache-Control: private, no-store`, and a signed-out call redirects, so `fetch` follows it and
  gets HTML: treat any non-JSON or non-200 answer as an error state in the dialog (not yet run).
- E2E: open a Note, edit, wait for "Saved", reload, the edit persisted.

## Out of scope

The version-conflict banner (04), the pin, color, label, archive and trash toolbar buttons, the
read-only variant for a Trashed Note, a full-screen layout on mobile (14), the full-Note read
itself (03.03.01).

## Acceptance criteria

- [x] Clicking a Note card opens the dialog with its current title and body, including a body
      longer than the card preview.
- [x] Typing stops for 1s, the status shows "Saving…" then "Saved", and "Saved" fades after about
      2s.
- [x] Blurring a field, closing the dialog, or hiding the tab flushes immediately.
- [x] Closing and reopening, or refreshing, shows the saved content, and the grid card shows it
      too.
- [x] The dialog traps focus, closes on Escape, and returns focus to the card.

## Testing expectations

E2E (Playwright, signed in as the test Owner): edit and reload; a body longer than the preview
opens in full; Escape closes and the edit is saved. Accessibility: the dialog and the live
region are named and announced (an axe check, as the repo already runs). The hook and the action
are covered by 03.02 and 03.01; the full-Note read by 03.03.01.

## Demo instructions

Open a Note, edit the title and body, watch the status region, stop typing, confirm "Saved",
refresh, and the edit persisted.

## Likely files/areas

`components/notes/NoteEditorDialog.tsx`, `components/ui/dialog.tsx`,
`components/notes/NoteCard.tsx`, `e2e/`.

## Risks / conflict hotspots

Closing the dialog while a save is in flight must not lose the queued edit. The grid must show
the new content after a save without a manual refresh.

## Decisions

- **The dialog owns its open state and takes the card's opener as a prop** (`trigger`). The
  `Dialog` primitive's own trigger then hands focus back to the card on close, with no focus code
  of ours. The card's opener is one transparent `<button>` that covers the card, so the title stays
  an `h2` and the preview a `p` (no block content inside a button). Its name is `Open note: <title>`
  (`Open note` for an untitled Note).
- **The content mounts only while the dialog is open.** Each opening reads the Note afresh, the form
  starts from what the read returned (which is what `useAutosave` treats as already saved), and
  nothing from an earlier opening lingers.
- **Close flushes in two places.** Every way of closing runs `flush()` first (Escape, backdrop,
  the close control), and the hook flushes on unmount as well. The first is the one the ticket
  asks for; the second is the safety net for a close the dialog does not see.
- **`Saved` fades with a CSS animation over its last 0.5s, not with state.** The hook returns to
  `idle` after 2s and the text goes with it, so nothing keeps a stale string for a screen reader.
  The region is `role="status"` with `aria-live="polite"` and stays mounted while idle, because a
  live region is announced only when its text changes. The animation is off under
  `prefers-reduced-motion`.
- **Error copy** (added to `ui-spec.md` section 16): both fields empty shows "A note needs a title or
  a body", any other failure shows "Could not save. Your changes are kept here." The raw zod message
  of a validation error is never shown.
- **No `axe-core` dependency was added.** The repo has no automated axe run (it appears in the ui-spec
  as a future CI pass, ticket 15), so the E2E asserts the accessible names and the live region, and
  an axe pass over the open dialog was run by hand (0 violations; see the last comment).
- **`@radix-ui/react-dialog` was added** for the shadcn `Dialog` primitive, the one new dependency.

- 2026-10-30 (from the 03.01 review): every successful save calls `revalidatePath("/")`, so the
  grid under the open dialog re-renders and moves the Note to the top while the Owner types.
  The dialog must keep its own `version` from each save's result, never from grid props. If the
  re-render proves costly or jarring, revalidate only on flush or close. `updateNote` can
  return `validation` with a raw zod message (for example for a bad `version`), so the status
  region should show a generic message for validation errors it did not author. An update that
  leaves both fields empty is rejected by design, so the dialog must show that failure.
- 2026-10-30 (from the 03.02 review): `useAutosave` returns `{ status, flush }` with `status`
  as `idle | saving | saved | error`. The dialog owns the copy and look of `error` (add it to
  `ui-spec.md` section 16; the hook only reports it). A failed save leaves the text unsaved and
  does not retry on a timer, so the next edit or flush re-sends it. `flush` reads the values
  from the last committed render and keeps the same identity across renders, so call it from
  event handlers and the E2E should type and close at once to prove nothing is lost. The hook
  flushes on unmount too, so a close that calls `flush()` first finds nothing left to send.
  `save` is called with `{ title, body }` only: the closure must add the Note's `id` and the
  `version` it keeps from each result (never from grid props), and may be a new function each
  render. A `save` that throws, or returns `{ ok: false }`, both show as `error`. Until 04, a
  stale version shows `error` and every later edit re-sends the same stale version.
- 2026-11-21: implemented on branch `cursor/note-editor-dialog-8991` (version bump v0.2.52 in its own
  commit). `NoteEditorDialog.tsx` has 18 unit tests (jsdom, `updateNote` and `fetch` replaced) and
