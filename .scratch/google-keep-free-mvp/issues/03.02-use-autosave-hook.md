# 03.02: `useAutosave` hook

**Status:** ready-for-agent
**Lane:** Standard (the concurrency logic in the autosave design, with no screen to catch a mistake)
**Parent:** 03-edit-a-note-with-autosave.md
**Blocked by:** None (the save function is injected, so it does not need 03.01)
**Unblocks:** 03.03

## Purpose

A client hook turns a stream of edits into saves: debounced, flushed on demand, one in flight at
a time, with a status a screen can show.

## Scope

- `components/notes/use-autosave.ts`: takes the current values and a `save` function it is
  given, and returns the status (`idle | saving | saved`) and a `flush()`.
- Debounce: 1 second after the last edit.
- Flush, bypassing the timer: `flush()` for blur and dialog close, and a `visibilitychange`
  listener (best-effort, as the spec says).
- Serialization: only one save in flight; an edit made mid-save is queued and sent right after
  the in-flight save resolves. The queue holds the latest values only.
- Status: `saving` while in flight, `saved` for about 2 seconds, then back to `idle`. The
  `conflict` state is added by 04.
- The hook never calls a Server Action itself. 03.03 passes `updateNote` in.

## Out of scope

The `conflict` state and its banner (04), the `updateNote` action (03.01), the dialog and its
live region (03.03), retry after a failed save.

## Acceptance criteria

- [ ] Typing stops for 1s, then exactly one save fires with the latest values.
- [ ] A flush saves immediately and cancels the pending timer, so the same edit is not saved
      twice.
- [ ] A flush with nothing changed since the last save does not call `save`.
- [ ] While a save is in flight, newer edits never start a second save. The latest edit is sent
      once, right after the first resolves.
- [ ] The status goes `saving` then `saved` then `idle` after about 2s.
- [ ] Hiding the tab triggers a flush.

## Relevant spec sections

Autosave section (Debounce, Flush, Serialization, Status feedback).

## Architecture/design constraints

All debounce, flush and queue logic lives in this hook, not in the Server Action (spec,
Autosave). The hook has one public surface (`flush`, status) and hides the timer, the in-flight
flag and the queue, so 04 can add a conflict state without touching callers.

## Testing expectations

Unit, with fake timers and a fake `save` that the test resolves by hand: every acceptance
criterion above, plus unmount mid-timer. Each test is seen failing for the intended reason
(for example, serialization with the in-flight guard removed). No E2E: no screen yet.

## Demo instructions

Run the unit suite and read the cases: debounce, flush, queued edit, status sequence.

## Likely files/areas

`components/notes/use-autosave.ts` and its test file.

## Risks / conflict hotspots

A save that fails has no defined behavior yet (04 covers conflicts only). The hook must not
swallow the failure silently: decide in scope-check whether it surfaces an `error` status now or
leaves it for 04.
