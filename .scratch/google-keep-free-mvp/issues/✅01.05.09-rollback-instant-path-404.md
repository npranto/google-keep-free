# 01.05.09: Rollback instant path returns 404

**Status:** closed (not fixed, by the owner's decision)
**Lane:** Standard (release tooling used under pressure)
**Parent:** ✅01.05-vercel-deploy.md
**Blocked by:** None
**Unblocks:** None

## Purpose

Make the Rollback workflow's instant path work, so an undo takes seconds and does not depend on the slower rebuild fallback. See `docs/incidents/0001-production-database-credential-rejected.md`.

## Scope

- Find why `npx vercel rollback "$DEPLOYMENT" --timeout 5m --token "$VERCEL_TOKEN"` fails with `Error: User not found. (404)` in run 38687492324 (2026-10-15 01:34:43 EDT), while the same workflow's earlier runs on 2026-10-09 succeeded.
- Fix the cause in `.github/workflows/rollback.yml` or in the repository secrets (`VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`). Rotating a secret is a human-only step: hand it to `mattpocock-skills:wizard`, and never ask for the token in chat.
- Prove it with a `dry_run` and then a real run, and record which path each took.

## Out of scope

Changing the rebuild fallback, promoting deployments, and any other workflow.

## Acceptance criteria

- [ ] A Rollback run with an existing target deployment takes the instant path and reports success, with no `User not found` error.
- [ ] The run summary says which path it took.
- [ ] A dry run resolves the target and reports that Production was not changed.

## Testing expectations

Manual: run the workflow with `dry_run` on, then once for real against a throwaway state the owner agrees to (the owner decides when a real rollback is acceptable). Record the run links.

## Decisions

### Close without the fix (2026-10-26, decided by the owner)

- **Pick:** close the ticket. The cause of the `User not found. (404)` was never found and the instant path was not changed.
- **Not done:** all three acceptance criteria stay unchecked on purpose. The Rollback workflow's instant path is presumed still broken: nothing was run to show otherwise.
- **What still covers the risk:** the workflow falls through to the rebuild path, which restored service in about a minute during the 2026-10-15 incident. An undo takes minutes, not seconds.
- **Reopen if:** a rollback is needed and the rebuild path is too slow or also fails, or before a release whose undo has to be fast (for example one that writes to user data).

## Comments

- 2026-10-15: filed from the postmortem (action item 4). In the incident the fallback rebuilt v0.2.23 in about a minute, so the undo still worked. The 404 may mean the token's user or team scope changed, or the deployment lookup used the wrong scope: not investigated.
