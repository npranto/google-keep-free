# 02.02.03: getActiveNotes and owner-scoped queries

**Status:** in-progress
**Lane:** Standard (`queries.ts` is a shared hot file that every later view builds on; authz lives here)
**Parent:** 02.02-create-note-action-and-active-notes-query.md
**Blocked by:** 02.02.02

## Before this ships

- From the 02.01 review: check the `getActiveNotes` query plan with `EXPLAIN` against the
  `(owner_id, state)` and `(owner_id, updated_at)` indexes, and record the result.
- `drizzle(sql)` in `lib/db/index.ts` has no `{ schema }`, so `db.query.notes` is
  unavailable. The queries use `db.select().from(notes)` and do not need it.

## Purpose

Let the server list the signed-in Owner's Active Notes, and make it impossible for any
later view query to forget the Owner filter.

## Scope

- `lib/notes/queries.ts`: private `selectOwnedNotes(...where)` that calls `getOwnerId()`
  itself and orders by `pinned DESC, updated_at DESC`, and `getActiveNotes()` on top of it.
- Integration tests in `lib/notes/notes.integration.test.ts` (harness from 02.02.02).

## Out of scope

Any UI, the other view queries, pagination, rate limiting.

## Acceptance criteria

- [ ] `getActiveNotes()` returns only the caller's Active Notes. A second Owner's session
      never sees them.
- [ ] Archived and trashed Notes are not returned.
- [ ] Notes come back pinned first, then most recently updated first.
- [ ] No exported function takes an Owner id.

## Testing expectations

Integration (real database, `getOwnerId` mocked): two Owners each with Notes, switching
the mock shows each only their own; a non-active Note is excluded; the order holds.
Nothing is user-visible yet, so no E2E.

## Decisions

### How does a query get its Owner? (2026-10-13, proposed by agent, approved by user 2026-10-14 at scope-check)
- **Pick:** A. `selectOwnedNotes(...where)` calls `getOwnerId()` itself, and `createNote` (02.02.02) puts `ownerId: await getOwnerId()` in its insert. No caller passes an Owner.
- **Rejected:** B, callers pass the Owner id. Every future query would have to remember it, and a wrong id compiles. C, Postgres row-level security: Neon's HTTP driver is stateless per query, so the Owner cannot be set once per request without a transaction on each call, and it adds a migration to Production by hand.
- **Evidence:** spec "Authorization" and ADR 0002 (inferred).
- **Principle:** make the wrong call impossible.
- **Undo:** trivial, it is code only.

### Scope-check (2026-10-14)
- **Files:** new `lib/notes/queries.ts` and additions to `lib/notes/notes.integration.test.ts`. Nothing is trimmed.
- **Safe because** `queries.ts` is new with no importers. *Traced.*
- **Regression checks:** `queries.ts` carries no `"use server"`; the `EXPLAIN` check seeds a few thousand rows under a random test Owner, because a near-empty table always gets a sequential scan; expect the plan to show `(owner_id, state)` plus a sort, since `(owner_id, updated_at)` cannot serve `pinned DESC, updated_at DESC`.
- **Abuse cases, each a test:** no exported function takes an Owner id (arity assertion); the caller's `...where` is combined as `and(eq(ownerId, ...), ...where)` so it cannot drop the Owner filter; no session means `getOwnerId` throws before any query runs; archived and trashed Notes are excluded.

### Review fixes (2026-10-14, approved by user at review: all should-fix plus the cheap nits)
- **Arity test replaced by a compile-time guard.** The scope-check named "an arity assertion", but `fn.length` is 0 for `(ownerId = "")` and `(...args)`, so it missed the real mistake, and it would go red on the planned `getNotesForLabel(labelId)` (`docs/architecture/system.md:44`, same file). It is now `// @ts-expect-error` on a call that passes an Owner id, so `npm run typecheck` fails if `getActiveNotes` gains a parameter, plus `toHaveLength(0)` for that one function. Each new query that must not take an Owner id adds its own line. Mutation M5 fails both checks.
- **Tie-breaker added:** `desc(notes.id)` after `updated_at`, so Notes with the same `pinned` and `updated_at` keep one order between requests. This extends AC3's order by one final key. A kept test seeds two Notes with the same timestamp and was seen red 3 of 3 runs before the fix.
- **Scope-check wording corrected:** the abuse case "the caller's `...where` is combined as `and(eq(ownerId, ...), ...where)`" has no direct test, because `selectOwnedNotes` is private by design. It is covered through the owner-scoping test, and mutation M7 (a caller `where` replaces the Owner filter) proves that test fails.
- Also fixed: the spy on `db.select` is restored in a `finally`, the unused seed is gone from that test, the comment above `selectOwnedNotes` no longer claims every Note read goes through it, and the duplicate import and redundant seed type are tidied.
- **Declined for now, recorded as follow-ups (user chose not to fix at review):** `import "server-only"` in `queries.ts` (a dependency decision, the repo uses it nowhere yet, no data leak without it); the `data-model.md` index note saying `(owner_id, updated_at)` serves the order (it cannot); payload size.

### The `next` 16.3.6 audit advisory (2026-10-14, user chose at quality-check: separate ticket, after this ships)
- **Pick:** do not bump `next` in this ticket. It is already tracked by `19-bump-next-security-advisories.md` (open, same six advisories, risk medium, single-purpose PR), so no new ticket was written.
- **Rejected:** bumping here, because a framework upgrade touches routing, `proxy.ts` and `@clerk/nextjs` and would widen a 21-line query change; accepting with no action, because the advisory is high severity.
- **Evidence:** `npm audit --omit=dev` on 2026-10-14 reports `next` 16.0.0 to 16.3.7 and now offers 16.4.1, where ticket 19 (written 2026-10-10) names 16.4.0. Ticket 19 should use whatever the fixed version is when it starts. This ticket did not touch `package.json`.
- **Principle:** one purpose per change.
- **Undo:** n/a, nothing changed.
