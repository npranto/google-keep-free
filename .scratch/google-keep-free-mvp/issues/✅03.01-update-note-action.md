# 03.01: `updateNote` Server Action

**Status:** closed
**Lane:** Standard (the first Owner-scoped write to an existing row, with a version check)
**Parent:** 03-edit-a-note-with-autosave.md
**Blocked by:** None (02 is closed)
**Unblocks:** 03.03

## Purpose

A signed-in Owner's client can save a new title and body for one of their own Notes, and the
server applies it only if the Note is theirs and the version still matches.

## Scope

- `updateNote` in `lib/notes/actions.ts`: one atomic
  `UPDATE ... WHERE id AND owner_id AND version RETURNING`, setting title and body and
  incrementing `version` and `updated_at`. The Owner comes from `getOwnerId()`, never from the
  input (ADR 0002). Success path only.
- A zod schema for the input in `lib/notes/validation.ts`, sharing the title and body rules
  (limits, NUL, the "needs a title or a body" check) with `createNoteSchema`. Update's fields
  are required, never defaulted, so a partial payload cannot blank a body. `createNote` does not
  change.
- The `WHERE` also excludes Trashed Notes (read-only, CONTEXT.md).
- Zero rows returned (a stale version, a Note that is not the Owner's, a missing id, or a
  Trashed Note) returns `{ kind: "not_found" }`, added to `ActionError`, and changes nothing.
  Telling a stale version apart is ticket 04.
- Returns `{ id, version }`, as `createNote` does.
- `revalidatePath("/")`, as `createNote` does.

## Out of scope

Version-conflict handling and its distinct error kind (04), the autosave hook (03.02), any UI
(03.03), pin, color, labels, archive and trash fields.

## Acceptance criteria

- [x] Updating an Owner's Note with its current version saves the new title and body, increments
      `version` and `updated_at`, and returns the new version.
- [x] Updating with a stale version changes nothing and returns an error.
- [x] Updating another Owner's Note id changes nothing and returns the same error as a missing
      id, so it does not reveal whether the Note exists.
- [x] Updating a Trashed Note changes nothing and returns the same error.
- [x] Invalid input (over the limits, a NUL character, a missing title or body field, both
      fields empty or whitespace) returns a validation error and writes nothing.
- [x] `createNote` behaves exactly as before (its existing tests pass unchanged).

All six are proven on local by the unit and integration tests. None could be driven on the
preview or on production, because nothing calls the action until 03.03; the sixth was also run
on the preview by the composer E2E specs.

## Relevant spec sections

Autosave section (Version handling); Authentication and authorization.

## Architecture/design constraints

`updateNote` stays a plain "save this version" call. Debounce and serialization live in the
client hook, not here (03.02). Follow the shape of `createNote`: the `ActionResult` return, the
session-derived Owner, no try/catch around `getOwnerId`.

## Testing expectations

Integration (real database, the existing harness in `lib/notes/notes.integration.test.ts`):
persists and increments `version` and `updated_at`; a stale version is rejected; another
Owner's id is rejected. Unit: the input schema's limits. No E2E: nothing a user can see changes
until 03.03.

## Demo instructions

Run the integration suite and read the three cases: success, stale version, other Owner.

## Likely files/areas

`lib/notes/actions.ts`, `lib/notes/validation.ts`, `lib/notes/notes.integration.test.ts`,
`lib/shared/result.ts` (a new error kind if one is needed).

## Risks / conflict hotspots

`lib/shared/result.ts` and `lib/notes/actions.ts` are shared with 04, which adds the conflict
error kind. Keep the new kind minimal so 04 extends it instead of reworking it.

## Decisions

### An update that leaves both fields empty (2026-10-29, user, scope-check)
- **Pick:** reject it with a validation error, the same rule as `createNote`. The last saved content stays.
- **Rejected:** allow it, because it saves a blank card with nothing to click and no way to remove it until trash (07).
- **Principle:** keep one invariant in one place (no empty Notes in the database, spec line 82).
- **Flips when:** delete or trash exists and the product wants Keep's "empty Note is discarded on close".
- **Consequence:** 03.02 and 03.03 must handle a failed save and show it.

### Trashed Notes cannot be updated (2026-10-29, user, scope-check)
- **Pick:** add `state <> 'trashed'` to the update's `WHERE`; a Trashed Note returns the same error as a missing one.
- **Rejected:** leave it to the UI, because read-only would then live only in a dialog that does not exist yet.
- **Principle:** enforce the invariant at the server boundary, not in the caller.

### Error for zero rows until 04 (2026-10-29, user, scope-check)
- **Pick:** one kind, `not_found`, for every zero-row case, including a stale version. 04 adds `conflict` and the follow-up read.
- **Rejected:** add both kinds now and report `conflict` for every zero-row case, which pulls 04 into this ticket and mislabels a foreign id.
- **Principle:** do not build the next ticket early.
- **Undo:** trivial; 04 changes the stale case.

### Return value (2026-10-29, scope-check default, not asked)
- **Pick:** `{ id, version }`, as `createNote` does, not `ActionResult<Note>` from `flows.md`, which would send `ownerId` to the client.
