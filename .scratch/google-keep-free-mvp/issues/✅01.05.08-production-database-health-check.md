# 01.05.08: Production database health check

**Status:** closed
**Lane:** Standard (a change to the build that can stop every deploy)
**Parent:** ✅01.05-vercel-deploy.md
**Blocked by:** None
**Unblocks:** None

## Purpose

Prove each environment's database credential works before a deploy can serve users, so a rejected `DATABASE_URL` stops the build and not a person loading the page. Production keeps serving the last good version, so nothing needs a rollback. See `docs/incidents/0001-production-database-credential-rejected.md`.

The Production `DATABASE_URL` is a Vercel sensitive variable that cannot be pulled, so the only place that can use it before the deploy goes live is the Vercel build itself.

## Scope

- A `prebuild` script in `package.json` that runs the existing connectivity check (`lib/db/check-connection.mts`, a `select 1` through `lib/db`). npm runs `prebuild` before every `npm run build`, so it covers Vercel Preview builds, Vercel Production builds, the GitHub `build` job and local builds, each against its own `DATABASE_URL`.
- Make the check work with no `.env.local`: use `--env-file-if-exists=.env.local` in place of `--env-file=.env.local`. As written, Node exits with an error when the file is missing, which would fail every Vercel and CI build. Preferred shape: change `db:check-connection` that way and set `"prebuild": "npm run db:check-connection"`, so there is one source of truth.
- The verification skill's feature map (`.claude/skills/verify-google-keep-free/`): the first read of a database-backed page on Production is named as covered by this build check, and not by a signed-in load.

## Out of scope

A public `/api/health` route and a `@smoke` E2E for it, uptime monitoring or alerting (a follow-up ticket for drift after a deploy, such as a Neon password reset), a signed-in test account on Production, feature flags, a query timeout or retry, and any change to `lib/env.ts`.

## Acceptance criteria

- [ ] With a valid `DATABASE_URL`, `npm run build` runs the check first, it passes, and the build continues.
- [ ] With a credential Neon rejects, the check exits 1, the build stops before `next build`, and the log names the cause (for example `password authentication failed`) without printing the connection string.
- [ ] The check runs when there is no `.env.local` (Vercel, GitHub Actions) and still loads it when it exists (local).
- [ ] On Vercel, a Preview deployment with a deliberately wrong `DATABASE_URL` fails at the check. This proves Vercel passes the sensitive variable to the build.
- [ ] The Production build uses the Production `DATABASE_URL`, and a failed Production build is not promoted, so Production stays on the previous deployment.

## Testing expectations

No new test files. The proof is behavior of the build:

- Run `npm run build` locally with a valid and with a wrong password (use a shell override, not an edit to `.env.local`) and record the exit code and the log.
- Run it with `.env.local` moved aside and `DATABASE_URL` set in the environment.
- Push a branch with a deliberately wrong Preview `DATABASE_URL` (restore it afterwards) and record that the Vercel build fails at the check. Record that a build with the old Production credential would have been stopped the same way.

## Decisions

- 2026-10-16: a build-time check replaces the original plan of a public `/api/health` route plus a `@smoke` E2E. The user wants to know before the deploy, and a post-deploy check leaves a bad credential live for about a minute and relies on rollback. The build is the only place that can use the Production credential.
- 2026-10-16: `prebuild` in `package.json`, not a Vercel-only `vercel-build` script. It also checks the database in the GitHub `build` job and in local builds. Cost: offline or credential-less builds fail at the check (fork and Dependabot PRs already fail `build` for the same reason, per the 02.03.01 decision).
- 2026-10-16: no route, no rate limiting, no query timeout or retry, no extra logging, no new tests. Reuse `lib/db/check-connection.mts` as it is, except for the env-file flag.
- 2026-10-16: accepted trade-off: a Neon outage or cold-start failure at build time blocks that deploy until a rebuild. It proves the build's credential, not the running function's, and the two are the same variable.
- 2026-10-16: uptime monitoring is a separate follow-up, because it covers drift after a deploy, which a build check cannot.
- 2026-10-16: review nit N1 declined: the failure log is the whole error object plus a Node module-type warning. It names the cause and leaks nothing, and the ticket reuses the check as it is.
