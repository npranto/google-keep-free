# 02.03.04: Composer title: Enter moves focus to the note field

**Status:** closed
**Lane:** Quick (one key handler and one assertion)
**Parent:** ✅02.03-composer-and-notes-grid.md
**Blocked by:** None
**Unblocks:** None

## Purpose

A keyboard user types a title in the composer and presses Enter to carry on into the note field, as `docs/design/ui-spec.md` section 18 says. Filed from the 02.03.02 review: the rule was found there and was out of that ticket's scope.

## Scope

- An Enter handler on the composer's Title field in `components/notes/Composer.tsx` that moves focus to the Note field. It does not save, close, or add anything to the title.
- One E2E assertion in `e2e/composer.spec.ts`.

## Out of scope

The other keyboard rules in ui-spec section 18, the note editor dialog (ticket 03), and any change to how the composer closes or saves.

## Acceptance criteria

- [x] With the cursor in Title, pressing Enter puts the cursor in Note, and the composer stays open and saves nothing.
- [x] Pressing Enter in Note adds a new line, as it does today.
- [x] Escape and Close still save a Note with content, as before.

## Testing expectations

An E2E assertion that Enter in Title focuses Note without saving (no Server Action request, no new card), in the existing composer spec. Keyboard path only, so no new screenshots.

## Decisions

### Scope-check: one structure, no trim (2026-10-22, proposed by agent)
- **Pick:** a key handler on the Title field plus a ref to the Note field, in the style of the file's Escape handler. No new state, dependency or abstraction.
- **Evidence:** Enter in Title did nothing before and the container's key handler only reacts to Escape *(traced)*. Moving focus inside the composer does not trigger the blur-save *(traced, then proven by the E2E test)*.
- **Undo:** trivial, revert the PR.

### Local proof run by hand (2026-10-22, user)
- **Pick:** manual, from a 13-step checklist on a production build.
- **Rejected:** automatic watched and hidden (screenshots, clip, Lighthouse) for the local target. Those ran on the preview instead.
- **Consequence:** the local score leaves out screens, performance and accessibility, and the manual walk came before the two review fixes below.

### Review nits N1 and N2: both fixed (2026-10-22, user)
- **Pick:** fix both. N1: the Title handler also skips `keyCode === 229`, because Safari ends an IME composition before the keydown. N2: two shared test helpers replace a copy of the same code in two tests.
- **Left alone:** the Escape guard in `Composer.tsx` has the same Safari gap. Changing it is outside this ticket.
- **Not proven:** the Safari branch. Playwright cannot drive an IME and there was no Safari run *(inferred)*.

### The build warning gets its own ticket (2026-10-22, user)
- **Pick:** file 02.04 (switch the package to `"type": "module"`) instead of touching `package.json` here.
- **Rejected:** folding it into this PR (unrelated to the composer, and it changes how every tool loads files).

### Production gap accepted (2026-10-22, user)
- **Pick:** close with criteria 1 to 3 not run on production. Production uses the real Clerk instance and has no test account.
- **Reason:** same accepted gap as 02.03.01 and 02.03.02. The criteria are proven on the preview (93 / 100, E2E 13 of 13) and the production smoke E2E and signed-out pages are clean.

### Follow-ups not ticketed (2026-10-22, user)
- **Pick:** file none of three proposed tickets. The findings stay recorded here: prettier is not enforced in CI (`format:check` is only a script and skips `e2e/`); the E2E workflow's `npx playwright install --with-deps chromium` step hung twice after its downloads (preview attempt 1, production attempt 1), costing 6 to 10 minutes and a manual re-run each time; the composer's Escape guard has the Safari IME gap.
